## Problem Statement

LAMT (Los Angeles Math Tournament) ran its first tournament on May 17, 2026 at UCLA: 180+ students from 8 counties, free, national-stage, one exam for grades 6-12. It was extremely successful. The website was built for that event and died with it: the homepage is now a "thank you for participating" screen with countdowns to dates that have passed. The organization is becoming a nonprofit, expanding to schools and international competitions, and the site no longer represents it. The founder wants a refresh, not a revamp: "our current website is effortlessly UCLA; refined, academic, but still welcoming." The current structure is good; the hero content is dead and there is zero email capture.

## Demand Evidence

- "We were successful but got so many emails saying they want to do more. We don't even have an email list." Direct, unprompted inbound demand from the first event. People contacted the org, asking for more, with no list to join.
- 180+ attendees and students from 8 counties at the first event, which was run with "scattered outreach" that the founder describes as "bad."
- Event ran at UCLA with a National stage and 100% free entry.

## Status Quo

The competitive ecosystem is crowded and prestigious: AMC, CMM, CMIMC, BMT, SMT, JHMT, BrUMO, HMMT, SCMC, AIME. LAMT's ambition is "flagship tournament like SMT/HMMT." The status quo for a school wanting competitive math for its students is to pick from these existing tournaments. HMMT (reference class) wins on proof density: mission, dates, news, sponsor wall, decade-deep archive. Its website is visually dated but irrelevant to its status.

LAMT cannot out-proof HMMT (25 years of archives) in year two. LAMT's scarce, manufacturable proof is demand: the inbound "we want more" emails. The email list is not a feature of the refresh, it is the flagship evidence.

## Target User & Narrowest Wedge

Chapters = schools that will join LAMT in future competitions. Outreach targets teachers, parents, AoPS forums, students. The narrowest wedge for the site: capture the inbound demand that is currently decaying (email list), while keeping the site's UCLA identity intact. Primary CTA of the refresh = email signup in the hero. Everything else stays as-is.

## Recommended Approach

**Visual refresh (v2 wireframe, approved):**
- Nav: unchanged (HOME, ARCHIVE, RULES, FAQ, ABOUT; REGISTER reappears when registration opens).
- Hero: UCLA blue, bear, same type. Dead countdowns + "Thank you for participating" replaced with: "We're just getting started." + "LAMT is becoming a nonprofit, and more is coming. Join the list and you'll know the moment we can say more." + one email field + "Notify me" button. The email block is primary in position (first above-the-fold CTA) but quiet in visual treatment — it inherits the hero's existing UCLA blue/gold rhythm, no new visual weight. That's the whole design tension resolved: primary placement, understated styling.
- Recap strip (new, thin, understated): links to results/archive, problems/solutions, and "a note from the LAMT Team" (replaces "apology letter" label — founder's wording).
- Sponsors + footer: unchanged.

**Backend (Railway + Postgres) — separate service, not in-repo:**
- next.config.js:3 sets `output: 'export'` — this repo builds to static files, and Next.js API routes do NOT run in static export. The backend must be a **separate Railway service** (founder's hosting decision), with CORS + env config pointing the static frontend at it. This is a prerequisite, not an open question.
- Backend service: Node (Express or Hono — small, fits the scope). Rate limiting: set `trust proxy` to the Railway hop count (`trust proxy: 1`, NOT `true` — naive `true` trusts any spoofed `X-Forwarded-For` and attackers rotate IPs to bypass limits). Rate-limit keying, one unambiguous sentence: **counter key = (IP, email) pair, 5/10min; plus 3/day per email regardless of IP** — a pure per-IP counter with 180 students behind campus NAT would throttle the whole venue. The 3/day email counter is shared across `/subscribe` and `/messages` (an attendee doing 1 subscribe + 3 messages is at the limit, correctly). Endpoints (public vs admin annotated per endpoint):

| Method | Path | Access | Purpose / payload |
|---|---|---|---|
| POST | `/subscribe` | PUBLIC | Email capture. Body `{ email }`. Validation, lowercased UNIQUE, (IP,email) rate limit, consent ts. Duplicate = 200 "already on the list". Re-subscribe clears `unsubscribed_at`, re-records consent, 200 "you're back on the list". Error contract: 400 `{ error }`, 429 `{ error, retryAfter }`, 200 `{ status: "ok" \| "already" \| "back" }`. |
| POST | `/unsubscribe` | PUBLIC | Tokenized link from first send, idempotent 200, soft-flag write. Body `{ token }`. Token = HMAC(email, UNSUBSCRIBE_SECRET — a separate env var from SESSION_SECRET, no secret reuse across purposes), 30-day expiry anchored to consent ts, one-use. Rate-limited 10/15min per IP; error contract 400 `{ error }` (invalid/expired token), 429 `{ error, retryAfter }`. If CSV export send path is chosen instead of an API send, tokens are pre-generated at capture time (the endpoint must not assume send-time generation). |
| GET | `/subscribers` | ADMIN | Email list viewer (added 2026-08-16 — admin tab lists emails, consent date, active/unsubscribed, copy-all for outreach). Sorted consent_at DESC. |
| GET | `/announcements` | PUBLIC | Read-only list for polling. |
| POST | `/announcements` | ADMIN | Body `{ title?, body, priority? }` — priority feeds the schema delta, default normal. |
| DELETE | `/announcements/:id` | ADMIN | Retraction — broadcast typos/errors must not be permanent. Origin-checked. |
| GET | `/schedule` | PUBLIC | Full schedule incl. change reasons. |
| POST | `/schedule` | ADMIN | Body: schedule item `{ time, end, event, location }` — no change reason on create (fresh item). |
| PATCH | `/schedule/:id` | ADMIN | Body `{ time?, end?, event?, location?, adjustmentReason? }` — adjustmentReason required on any time change (the timeline displays it), optional otherwise. (PATCH, not POST — same verb convention as messages.) |
| DELETE | `/schedule/:id` | ADMIN | Cancelled/removed schedule item — "adjustmentReason" can't express "this event isn't happening." Origin-checked. |
| GET | `/messages` | ADMIN | Contact inbox. |
| POST | `/messages` | PUBLIC | Body `{ name, email, message }`. (IP,email) rate limit, separate 5/10min counter from subscribe. Error contract: 400 `{ error }` (validation), 429 `{ error, retryAfter }`. |
| PATCH | `/messages/:id` | ADMIN | Discriminating payload: `{ resolved: true }` OR `{ reply: { body } }`. Reply author derived from session (never client-supplied). Reply does NOT auto-resolve; resolve is explicit (matches current UI). |
| GET | `/session` | ADMIN | Session status — lets the admin page distinguish "logged out" from "network error" instead of guessing at 401s. |
| POST | `/login` | PUBLIC | Body `{ password }`. Rate-limited 10/15min per IP, constant-time compare. Sets httpOnly signed cookie. |
| POST | `/logout` | ADMIN | Clears session cookie. |

Origin policy on every non-GET verb (POST, PATCH, DELETE): **missing Origin allowed (curl, non-browser clients); mismatched Origin rejected (browsers always send Origin on cross-site mutations).** No "reject everything" — it breaks testing.
- Admin auth server-side: session-cookie auth via a Railway route handler, no hardcoded password shipped to the browser. The current `ADMIN_PW = "BRUINSATLAMT"` at app/admin/page.tsx:9 dies. This restructures the admin page from a localStorage client component into an API client — the doc acknowledges that restructure explicitly.
  - CROSS-SITE INTERACTION (read before implementing): the session cookie is set on the **Railway domain** but fetched from the **static frontend host** — that's cross-site. `SameSite=Lax` will NOT attach to XHR from another origin. Required: `SameSite=None; Secure` cookie, CORS with `credentials: true` and an exact-origin whitelist (apex AND www variants of the frontend host both whitelisted, or the admin silently 401s from one), plus an Origin check on **every non-GET verb** (POST, PATCH, DELETE) — not just POST. The PATCH endpoint is cookie-authenticated with `SameSite=None`, so a malicious page can use the admin's session to resolve/inject messages if the origin check is missing. Handle OPTIONS preflight on ALL routes — `SameSite=None` + credentialed cross-origin JSON mutations trigger a browser preflight on every PATCH/POST, and a naive Express route misses it and silently fails. Frontend host to whitelist: the current static host (to be named at implementation; the repo's deploy target today). Without these sentences, silent 401s and CSRF will eat hours.
  - Login flow: `ADMIN_PASSWORD` and `SESSION_SECRET` as SEPARATE env vars (the cookie-signing key is not the password), `POST /login` sets httpOnly signed cookie with a **fixed 12h TTL** (not sliding — a sliding refresh adds complexity for a 13-hour tournament day; logging in twice is fine), `POST /logout` clears it. Login is a public endpoint: rate-limit it (e.g., 10/15min per IP), require a high-entropy env password (the predecessor was "BRUINSATLAMT"), constant-time compare.
- Unsubscribe: capture stores opt-in consent (timestamp); the first send plan (Open Question 1) must include an unsubscribe mechanism. One line in the design, non-negotiable later.

**Live page full redesign (founder's explicit ask):**
- Current architecture is broken: admin writes announcements and messages to localStorage, which only syncs across tabs on the same device. Attendees never received announcements; contact form messages never reached staff. "Barely anybody used it" is downstream of this.
- Redesign: live timeline (happening now / next up), schedule with change reasons, venue cards, campus map, info/help, contact form wired to the backend inbox.
- Data model: existing ScheduleItem/Update shapes (app/live/types.ts) carry the timeline. VENUES (label, detail, map href — already in page.tsx) stay FRONTEND constants, promoted to typed data; they are NOT a backend schema delta. The schema deltas are exactly two: update priority + message state (resolved/replies — already in types.ts, must survive the transport swap). Migration story: raw SQL on Railway console (tournament-day cadence doesn't need a migration tool).
- Transport: polling every 30-60s is sufficient for tournament-day cadence; no WebSocket/SSE unless polling proves insufficient.
- "Campus map": reuse the existing OpenStreetMap embed (MAP_EMBED_SRC in page.tsx) — no custom SVG needed.
- Timeline derivation stays CLIENT-side: schedule times are "8:00 AM" strings, and now/next derivation (getTimelineState) must run on the attendee's clock, not the server's (server clock ≠ client clock, DST). The API serves data; clients derive. This also avoids serializing "now" over the wire. Known tradeoff (accepted, documented): a skewed attendee device shows a wrong "next up" on tournament day. If it ever matters, stamp server time in API responses and derive a client-server offset.
